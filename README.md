# geoguessrHost

Repository used to host the WebGL build and site assets for the Geoguessr project.

**Repository layout (after copying WebGL build)**

- `index.html`: Host page that initializes Unity and the host UI. Update paths here if build filenames change.
- `assets/`
  - `css/` : site styles (e.g. `assets/css/app.css`)
  - `js/` : host JavaScript (e.g. `assets/js/app.js`, `assets/js/unityBridge.js`, etc.)
  - `img/`, `fonts/`, ... : other static site assets
- `Build/` : Unity WebGL build output (copy this folder from the development repo)
  - `unity.loader.js`
  - `unity.framework.js`
  - `unity.data` (or `*.data.unityweb` depending on build)
  - `unity.wasm` (or `*.wasm.unityweb`)
- `TemplateData/` (optional) : Unity template files (CSS/icons) if present
- `StreamingAssets/` (optional) : only if your game uses streaming assets

**What to copy from the development repo (`geoguessr`)**

1. From `geoguessr/web/public/unity/Build/` copy the entire folder contents into `geoguessrHost/Build/`.
   - Copy files such as `unity.loader.js`, `unity.framework.js`, `unity.data` or `*.data.unityweb`, `unity.wasm` or `*.wasm.unityweb`, plus any `.symbols`, `.mem`, etc.
2. If present, copy `TemplateData/` (generated by Unity) alongside `index.html` or into `geoguessrHost/TemplateData/`.
3. Copy only the build output and any static runtime assets — do NOT copy `Assets/`, `Library/`, `ProjectSettings/`, or `.csproj` files from the Unity project.

**Post-copy checks and adjustments**

- Verify the filenames in `geoguessrHost/Build/`. Common names are `unity.data` or `unity.data.unityweb` and `unity.wasm` or `unity.wasm.unityweb`.
- Open [geoguessrHost/index.html](geoguessrHost/index.html) and confirm the `createUnityInstance` URLs match the actual filenames in `Build/` (e.g. `Build/unity.data` vs `Build/unity.data.unityweb`).
- Ensure `index.html` uses the correct relative paths for site assets (e.g. `assets/css/app.css`, `assets/js/app.js`).
- If your host JS uses ES module `import`/`export`, make sure the script tags include `type="module"`.

**Local test (serve and verify)**

1. From the `geoguessrHost` directory run a static server and open `http://localhost:8000`:

```bash
# Python
python -m http.server 8000

# or Node.js http-server
npx http-server -p 8000
```

2. In the browser DevTools > Network: verify `Build/*` files load (no 404) and `.wasm`/`.unityweb` files are served with correct MIME types.
3. In the Console: check for `createUnityInstance` success and any WebGL errors. If you see `INVALID_ENUM` or related WebGL errors, confirm files are not corrupted and that `index.html` points to the exact filenames.

**Deployment tips (GitHub Pages)**

- Push to the `geoguessrHost` repository (i.e. `monash-emerging-tech/geoguessrHost`) and enable GitHub Pages for the `gh-pages` branch or the repository's `main` branch `docs/` folder.
- GitHub Pages will serve static files; make sure `Build/` and `TemplateData/` are included in the branch you publish.

**Syncing web assets between repositories**

- When you add or change web assets (for example: files or folders under `assets/`, the Unity `Build/` output, `TemplateData/`, or `StreamingAssets/`), those changes must be reflected in both repositories:
  - Update the development repo (`geoguessr`) so the source files are present for local development and rebuilds.
  - Copy the runtime build and any new static assets into the host repo (`geoguessrHost`) so the live site can serve them.

This keeps the development source and the hosted runtime in sync and prevents missing resource 404s in production.
